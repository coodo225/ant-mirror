# 🐜 개미들을 위한 투자정보

> 개미는 정말 늘 반대로 가는가. 그래서 틀렸는가.

한국 증시를 **수급**으로 읽는 대시보드. 개인·외국인·기관 세 주체의 돈이 어디로 흐르는지를
중심에 놓고, 지수·종목·업종과 미국장·환율·금리·FOMC 같은 바깥 맥락을 한 화면에 붙였습니다.

서버가 필요 없습니다. 데이터 수집은 GitHub Actions 가 대신 돌고, 페이지는 정적 파일만 읽습니다.

---

## 이 페이지의 태도

"개미는 외국인·기관과 늘 반대로 간다"는 말은 대체로 사실입니다.
최근 3년(750거래일) 중 약 80% 의 날에 개인과 외국인은 정반대 방향이었고,
두 주체의 일별 순매수 상관계수는 −0.8 안팎입니다(화면의 숫자는 수집할 때마다 다시 계산됩니다).

다만 이건 산수가 아니라 **관찰**입니다. 개인·외국인·기관·기타법인의 순매수를 모두 더하면 0이라
누군가는 늘 외국인의 반대편에 서야 하지만, 그게 꼭 개인일 필요는 없습니다.

그래서 이 페이지가 던지는 질문은 방향이 아니라 **타이밍**입니다.
각 주체가 크게 사들인 날(그날 **거래대금 대비 순매수** 상위 20%)로부터 20거래일 뒤 지수가 어떻게 됐는지를
시장 평균과 비교해 **성적표**로 만듭니다. 실제 손익이 아니라 '산 시점'의 채점이고,
20일 수익률이 날마다 겹친다는 점을 감안한 90% 범위(블록 부트스트랩)가 0을 포함하면 학점을 C로 둡니다.
금액이 아니라 거래대금 대비 비율로 줄을 세우는 건, 3년 사이 거래대금이 2~3배 늘어 금액으로는
최근 날짜만 극단으로 뽑히기 때문입니다. 계산은 `collector/collect.py` 의 `build_ant()` 에 전부 들어 있습니다.

풍자는 톤에만 있고 숫자에는 없습니다. 데이터가 개미 편을 들면 페이지도 개미 편을 듭니다.
고정된 결론 문장은 두지 않고, 화면의 문장은 그날 숫자에서 만듭니다.
한계는 **"성적표를 믿기 전에 읽을 것"** 섹션에서 스스로 밝힙니다.

목적은 조롱이 아닙니다. 개미가 지는 이유가 멍청해서가 아니라 늘 마지막에 정보를 받기 때문이라면,
필요한 건 같은 숫자를 같은 시각에 보는 일입니다.

## 왜 이런 구조인가

브라우저에서 KRX·네이버·FRED·야후를 직접 `fetch` 하는 방법은 **작동하지 않습니다.**
확인해 보면 이렇습니다.

| 소스 | 응답 | `Access-Control-Allow-Origin` |
|---|---|---|
| KRX 정보데이터시스템 | 403 (로그인 필요) | 없음 |
| 네이버 금융 | 200 | **없음** |
| 한국은행 ECOS | 200 | **없음** |
| Yahoo Finance | 200 | **없음** |
| FRED | 200 | 없음 |

CORS 헤더를 주는 곳이 하나도 없어서, 브라우저는 응답이 도착해도 스크립트에 넘겨주지 않습니다.
그래서 수집은 서버 쪽(=GitHub Actions)에서 하고, 결과 JSON 을 페이지와 **같은 오리진**에 놓습니다.

```
GitHub Actions (cron)
  └─ collector/collect.py
       ├─ 네이버 증권        → 개인/외국인/기관 수급(현물·선물), 프로그램 매매, 지수 일봉·시세, 시총상위, 업종
       ├─ 한국거래소         → 공매도 거래·순보유잔고(시장 단위), 휴장일
       ├─ 한국은행           → 금통위 날짜
       ├─ 다음 금융          → 수급 예비 소스 (네이버 실패 시)
       ├─ FinanceDataReader  → 지수 일봉 예비 소스
       ├─ 금융투자협회       → 신용융자·예탁금·반대매매
       ├─ yfinance           → 미국 지수·선물·금리·환율·원자재
       └─ federalreserve.gov / FRED → FOMC·경제지표 일정, 매크로 지표
            └─ docs/data/*.json, og.png → data 브랜치에 최신본 한 커밋으로 덮어쓰기
                 └─ main 의 docs/(화면 코드) + 이번 데이터를 묶어 Pages 에 배포 → 페이지가 같은 오리진에서 읽음
```

또 하나 알아둘 것. **개인·외국인·기관 수급에는 진짜 실시간이 없습니다.**
장중에 나오는 값은 잠정치(추정)이고, 확정치는 장 마감 후 저녁에 갱신됩니다.
그래서 화면 상단에 장 상태 배지와 잠정치 안내를 띄우고, 마감 후 실행에서 확정치로 정정합니다.

## 빠른 시작

```bash
python -m venv .venv
```

```bash
.venv/Scripts/python -m pip install -r collector/requirements.txt
```

```bash
.venv/Scripts/python collector/collect.py
```

`docs/data/*.json` 이 생기면 정적 서버로 열어 봅니다. (`file://` 로 열면 fetch 가 막힙니다.)
수집기를 돌리지 않고 지금 배포된 데이터를 그대로 받아 보려면 data 브랜치에서 꺼냅니다.

```bash
git fetch origin data
```

```bash
git archive FETCH_HEAD docs | tar -x
```

```bash
.venv/Scripts/python -m http.server 8765 --directory docs
```

브라우저에서 `http://localhost:8765` 로 접속합니다.

> macOS / Linux 는 `.venv/Scripts/python` 대신 `.venv/bin/python` 을 씁니다.

### 테스트

수집기 테스트는 외부 소스를 전부 가짜 데이터로 바꿔서 돌기 때문에 네트워크가 필요 없습니다.
소스가 죽거나 멈췄을 때의 동작(직전 정상본 유지, 멈춤 감지, 예비 소스 병합, exit 3)과
통계 함수(순매수 강도, 90% 범위, 학점)를 확인합니다. 코드를 푸시하면 Actions 에서도 자동으로 돕니다.

```bash
.venv/Scripts/python -m pip install -r requirements-dev.txt
```

```bash
.venv/Scripts/python -m pytest -q tests
```

## 배포 (GitHub Pages)

1. 이 폴더를 GitHub 저장소로 올립니다.
2. **Settings → Pages → Source** 를 `GitHub Actions` 로 지정합니다.
3. **Actions** 탭에서 `시장 데이터 수집` 을 한 번 수동 실행(`Run workflow`)해 봅니다.
   첫 실행이 `data` 브랜치를 만들고 사이트를 배포합니다.

수집 결과는 main 에 커밋하지 않습니다. 최신 데이터 한 벌만 `data` 브랜치에 부모 없는 커밋으로 덮어쓰므로
저장소가 데이터 이력으로 불어나지 않습니다(대신 데이터 변경 이력은 남지 않습니다).
화면 코드(`docs/`)를 main 에 올리면 `사이트 배포` 워크플로가 data 브랜치의 최신 데이터와 묶어 바로 배포합니다.

GitHub 의 예약 실행(장중 30분마다, 18:17, 20:23, 07:37)도 걸어 두었지만, 부하가 몰리면 늦어지거나 빠집니다
(2026-09~10 실측: 장중 갱신이 하루 2번꼴, 13시 이후는 거의 없음). 장중 숫자를 매매에 쓰려면 아래
**장중 5분 갱신**을 켜 두세요. 화면은 5분마다 새 수집이 있는지만 확인하고, 헤더에 '수집 HH:MM (N분 전)'을 띄웁니다.

### 장중 5분 갱신 (외부 스케줄러, 무료, 설정 약 20분)

외부 스케줄러가 GitHub API 로 `시장 데이터 수집` 워크플로를 **하루 종일 5분마다** 깨웁니다.
워크플로는 깨어날 때마다 `collector/mode.py` 로 할 일을 고르므로, 시간대를 따로 나눌 필요가 없습니다.

- 장중(거래일 08:55~15:40): 1시간 안에 전체 수집이 있었으면 **가벼운 수집**(수급 오늘 행·분 단위 흐름, 프로그램 매매, 지수 시세 — 요청 약 12번, 수 초), 아니면 전체 수집
- 장 전(07:30~08:55) 한 번, 마감 뒤(15:40~20:05) 1시간에 한 번, 20시 확정(20:05 이후) 한 번 **전체 수집**
- 밤(21:30~07:30)과 2.5분 안의 중복 호출은 **건너뜀**(몇 초 만에 끝남). 휴장일·주말은 6시간에 한 번 전체 수집
- 350종목 범위는 새 거래일 데이터가 생겼을 때와 18시 이후 한 번만 다시 받습니다
- Actions 탭의 `Run workflow` 버튼으로 돌릴 때 `force` 를 켜면 시간대와 상관없이 전체 수집합니다

1. **토큰 만들기**: GitHub → Settings → Developer settings → Personal access tokens → **Fine-grained tokens** → Generate new token
   - Repository access: **Only select repositories** → 이 저장소 하나만
   - Permissions → Repository permissions → **Actions: Read and write** (다른 권한은 주지 않습니다)
   - Expiration: 1년(만료 전에 다시 만들어 바꿔 끼웁니다)
   - 토큰은 채팅·이슈·저장소 어디에도 붙여 넣지 마세요. 새면 바로 Revoke 하면 됩니다.
     이 토큰으로는 워크플로 실행·취소만 할 수 있고 코드나 시크릿은 바꿀 수 없습니다.
2. **cron-job.org** 에 가입하고 작업(Cronjob)을 하나 만듭니다.
   - URL: `https://api.github.com/repos/<계정>/<저장소>/actions/workflows/collect.yml/dispatches`
   - Request method: **POST**, Request body: `{"ref":"main"}`
   - Headers: `Authorization: Bearer <토큰>`, `Accept: application/vnd.github+json`, `X-GitHub-Api-Version: 2022-11-28`
   - Schedule: **Every 5 minutes**(매일, 하루 종일). 시간대는 상관없지만 Asia/Seoul 로 두면 기록 보기가 편합니다.
   - 실패 알림 메일을 켜 둡니다(연속 실패가 쌓이면 cron-job.org 가 작업을 멈춥니다).
3. 다음 장중에 Actions 탭에서 실행이 5분 간격으로 생기는지, 사이트 헤더의 'N분 전'이 10분 안팎인지 확인합니다.
   응답 코드 204 가 정상입니다.

요청량: 장중 가벼운 수집 하루 약 80번 × 12요청에 전체 수집을 더해 네이버 요청은 하루 3천 번 안팎입니다.
수집기는 하루 요청 수를 `meta.json` 에 이어 적고, 상한(`REQUEST_CAP`, 기본 3,500)을 넘으면 무거운 섹션(350종목, 종목 순위)을 건너뜁니다.

### 저장소는 public 을 권합니다

Actions 스케줄 실행은 **public 저장소에서 무료**입니다.
private 이면 하루 약 17회 실행이 무료 사용량에서 차감됩니다(1회 약 1~2분).
더 아끼려면 `collect.yml` 의 첫 cron 을 `7 0-6 * * 1-5`(1시간마다) 정도로 줄이세요.

> 참고: GitHub 는 60일간 활동이 없는 저장소의 예약 워크플로를 자동 비활성화합니다.
> 수집 워크플로가 실행할 때마다 자기 자신을 다시 켜 두는 API 를 부르므로(`예약 실행 유지` 단계) 따로 할 일은 없습니다.

## 하루 요약 받아 보기 (RSS · 텔레그램)

거래일마다 지수와 주체별 순매수, 브리핑을 한 항목으로 묶은 Atom 피드를 만듭니다.
20시(KRX 확정) 전 수집분은 제목에 `(잠정)`이 붙고, 그 뒤 수집분이 확정본으로 덮어씁니다.

- 피드 주소: `https://<계정>.github.io/<저장소>/data/feed.xml` (RSS 리더에 그대로 넣으면 됩니다)

텔레그램으로 받으려면(선택) 봇을 만들어 저장소 시크릿 두 개를 넣습니다. 그러면 매일 확정 요약을 한 번 보냅니다.

1. 텔레그램에서 `@BotFather` 에게 `/newbot` 을 보내 봇 토큰을 받습니다.
2. 만든 봇에게 아무 메시지나 보낸 뒤 `https://api.telegram.org/bot<토큰>/getUpdates` 를 열어 `chat.id` 를 확인합니다.
3. **Settings → Secrets and variables → Actions** 에 `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID` 를 추가합니다.

토큰은 수집 경고에 섞여도 `***` 로 가려집니다.

## 선택: FRED API 키

미국 CPI·고용·PCE **발표 일정**과 CPI·기준금리·실업률 **실측치**를 함께 보려면
[FRED 무료 API 키](https://fred.stlouisfed.org/docs/api/api_key.html)를 발급받아
저장소 **Settings → Secrets and variables → Actions** 에 `FRED_API_KEY` 로 등록하세요.

없어도 나머지는 전부 정상 동작합니다. (미 노동통계국 BLS 사이트는 봇을 403으로 차단하므로
CPI 일정은 FRED 를 통해서만 자동으로 가져올 수 있습니다.)

로컬에서 쓸 때:

```bash
FRED_API_KEY=your_key .venv/Scripts/python collector/collect.py
```

## 화면 구성

| 섹션 | 내용 |
|---|---|
| **거울 한 줄** | 그날 개인의 매수 강도, 지수 방향, 반대편에 선 주체를 한 문장으로. 데이터가 지난 거래일이면 '오늘' 대신 날짜로 쓴다 |
| **수급 줄다리기** | 개인·외국인·기관·기타법인의 순매수/순매도를 좌우 발산 막대로(넷을 더하면 0). 위쪽 띠는 파는 진영과 사는 진영의 구성비 |
| **🐜 개미 온도계** | 그날 개인의 순매수 강도(거래대금 대비)가 3년 분포에서 몇 번째 백분위인지와 그날 지수 등락. 상·하위 20% 에 들면 과거 같은 국면의 20일 성적을 붙이되, 2009~2023 같은 계산 결과(시장 평균과 구분 안 됨)를 함께 적는다 |
| **외국인의 본심 (선물)** | 코스피200 선물 외국인 순매수 20일. 현물·선물 5일 합계가 둘 다 평소보다 클 때만 갈림/일치를 판단하고, 과거 같은 갈림 이후 20일 기록을 붙임 |
| **빚투 체온계** | 신용융자 잔고(코스피/코스닥), 반대매매 금액·비율, 투자자예탁금, 미수금 — 금융투자협회 공개 통계. 경보는 이 기간 자기 이력 대비 상위 구간일 때만 |
| **지금 벌어지는 일** | 연속 매매, 수급 구도, 환율·VIX·반도체 지수를 문장으로 정리 |
| **지수** | 코스피·코스닥 현재가와 60일 스파크라인 |
| **성적표** | 주체별 A~F 학점(3년 표본, 90% 범위가 0을 포함하면 C) + 연도별 분해 — 개미 학점이 장세 탓인지 검증 가능 |
| **반대로 가는 본능** | 개미↔외인·기관 상관계수와 정반대였던 날의 비율. 옆에는 순매수 합이 0이라는 구조와 그 한계 설명 |
| **개미가 크게 질렀던 날들** | 3년 중 순매수 강도가 가장 컸던 날 5일(서로 다른 국면)과 그 20거래일 뒤 성적. 잘 맞은 날도 그대로 표시 |
| **지금과 비슷했던 날들** | 오늘의 수급 강도+가격 조합과 가장 가까웠던 과거 5일(서로 20거래일 이상 간격), 그 20거래일 뒤 결과와 닮은 정도 |
| **개미 장바구니 vs 외인 장바구니** | 최근 60거래일 각자 담은 종목 TOP10(ETF 제외)과 '산 뒤 등락' 대결, 같은 기간 지수, 개미의 눈물/승리 |
| **성적표를 믿기 전에 읽을 것** | 표본·장세 편향·인과 한계에 대한 자기 고백 |
| **수급 흐름** | 40/120거래일 누적·일별 순매수 4개 선(또는 막대, 기타법인 포함) + 지수 종가 오버레이 |
| **연속 매매 기록** | 주체별(기타법인 포함) 연속 매매 일수와 최근 10일 매매 방향 점 |
| **기관은 누가 움직였나** | 금융투자·투신·연기금·보험·은행·기타금융 분해 |
| **프로그램 매매** | 코스피·코스닥 프로그램 순매수(차익·비차익) 60일. 오늘 규모는 최근 1년 확정치 중 위치로, 극단일 때만 순위를 말함 |
| **공매도** | 거래대금 대비 공매도 비중 120일(2025-03-31 전면 재개 뒤끼리만 비교), 순보유잔고(2거래일 늦음)와 그 변화 — 한국거래소 |
| **시가총액 상위 종목** | 면적=시총, 색=등락률 트리맵. 누르면 5일치 종목 수급과 60일 누적 순매수 차트, 주체별 '산 뒤 등락'(같은 날 지수 기준선과 함께) |
| **업종** | 상승·하락 상위 8개 업종 |
| **바깥 지표** | 미국 지수·선물, 반도체(SOX), VIX, 10년물, 환율, 달러인덱스, 유가, 금 |
| **다가오는 이벤트** | FOMC(점도표 여부 포함)·금통위·선물옵션 만기·증시 휴장 D-day. FRED 키가 있으면 CPI·고용·PCE 추가 |

색은 한국 관례를 따릅니다. **빨강 = 상승·순매수, 파랑 = 하락·순매도.**

## 국내 장 일정 (휴장일 · 금통위 · 만기)

`collector/krx_calendar.json` 에 휴장일, 정규장 시간이 다른 날(수능일), 금통위 날짜를 적어 둡니다.
수집기는 이 목록을 바탕으로

- KRX(휴장일)와 한국은행(금통위)에서 일주일에 한 번(다음 해 일정이 아직 공표되지 않았거나 지난번에 실패했으면 하루에 한 번)
  다시 받아 `docs/data/calendar.json` 에 이어 둡니다. 공식 목록이 이기지만 이 파일에 손으로 더한 날짜는 늘 합칩니다.
  공식 소스가 막히면 네이버 증시 캘린더(앞으로 약 90일)에서 찾은 휴장일·금통위를 더하고, 그것도 안 되면 적어 둔 목록을 씁니다.
- 새해 첫 거래일 10시 개장은 해마다 저절로 반영합니다.
- 선물·옵션 만기(매월 두 번째 목요일, 휴장일이면 앞당김. 3·6·9·12월은 동시만기)를 휴장일 목록으로 계산합니다.
- 휴장일 아침에도 장 상태를 '휴장일'로 띄우고, 데이터 멈춤 판단에서 휴장일을 거래일로 세지 않습니다.

**해마다 할 일**: 다음 해 수능일(장 10:00~16:30)을 `special_sessions` 에 더하고, 연말에 다음 해 휴장일·금통위를 확인합니다.
(공식 소스가 받아지면 휴장일·금통위는 저절로 채워지지만, 수능일 장 시간은 자동 소스가 없습니다.)

그 밖에 자동 수집원이 없는 일정은 `collector/events_seed.json` 에 적으면 화면에 함께 표시됩니다.

```json
{
  "events": [
    { "type": "실적", "date": "2026-10-29", "title": "삼성전자 3분기 실적 발표", "impact": "mid" }
  ]
}
```

## 데이터에 대한 주의

- 네이버·다음 금융은 공식 API 가 아닙니다. 응답 구조가 예고 없이 바뀌면 수집이 깨질 수 있고,
  대량 요청은 서비스 약관에 저촉될 수 있습니다. 개인용 갱신 주기를 지키세요.
  실제로 옛 수급 페이지(`finance.naver.com/sise/investorDealTrendDay.naver`)는 2026-09-17 폐지됐고,
  지금은 Npay 증권 페이지가 쓰는 `stock.naver.com/api/domestic/market/trend/daily` 를 씁니다.
  KRX 정보데이터시스템의 일반 통계는 2025-12 회원제로 바뀌어 비로그인으로 받을 수 없습니다.
  공매도는 네이버·다음 종목 화면이 띄우는 KRX 공매도 임베드 경로를 쓰는데, 이 경로도 언제든 막힐 수 있어
  실패하면 직전 값을 두고 화면에 '지난 데이터'로 알립니다(부가 섹션이라 워크플로를 실패로 만들지 않습니다).
- 소스가 실패하거나 멈추면 그 섹션은 **직전 정상 데이터를 유지**하고, 화면 맨 위에 '지난 데이터' 안내가 뜹니다.
  핵심인 코스피 수급·일봉이 갱신되지 않으면 워크플로가 데이터를 올리고 배포한 뒤 **실패로 표시**되어 GitHub 알림이 갑니다.
- 장중 수급은 잠정치입니다. 확정치는 장 마감 후에 나옵니다.
- 지수 수급 단위는 **억원**, 종목 수급 단위는 **주**입니다.

## 면책

이 프로젝트는 공개된 시장 데이터를 정리해 보여주는 **정보 도구**입니다.
투자 자문이나 매매 권유가 아니며, 수치에 오류나 지연이 있을 수 있습니다.
투자 판단과 그 결과에 대한 책임은 투자자 본인에게 있습니다.
